ROS2 Pi 5 Autonomous Car

Real-time mapping with LiDAR, a depth-based safety layer, and a Flask + Socket.IO control page built from scratch.

Project Demo View on GitHub
  • Deterministic left-hand wall-follow maneuver instead of opaque autonomy
  • Naive ROS2 LiDAR map plus a depth “guard” that can override manual input
  • Soft PWM ramps to reduce jerk and protect the chassis during starts/stops

Demo

The car navigates around a bottle barricade using the depth safety layer and the live control UI.

Depth Guard

Computes a median distance inside a front-center ROI and uses hysteresis to avoid flicker. If the distance is unsafe, motors stop immediately.

Wall-Follow Maneuver

On command, the car backs up, performs a capped left probe, and advances in short pulses while maintaining a controlled gap to the obstacle line.

Live UI

Depth preview, an obstacle bar, and a naive LiDAR map stream provide real-time observability during testing and tuning.

Software

System layout

  • server.py initializes the depth camera, launches a Depth Guard thread (safety), optionally spins a ROS2 node for LiDAR, and runs the mapping loop that renders a JPEG map.
  • Routes: /move (manual drive; forward is blocked when the guard is active), /maneuver_depth (left-hand bypass), /video_feed (depth MJPEG), /naive_map_feed (map MJPEG), plus lightweight debug endpoints.
  • Socket.IO emits obstacle_update for low-latency UI feedback; if websockets are unavailable, the UI polls /debug_distance.
  • Motor helpers wrap GPIO with PWM ramps to smooth acceleration and braking.

Why this looks like a real system

  • Separate threads for sensing, safety, mapping, and UI → clearer failure isolation and simpler debugging.
  • Safety layer can override operator input → predictable behavior near obstacles.
  • Continuous streams (depth + map) → direct observability during bring-up and tuning.

Control UI (screenshots)

Safety & motor control

  • Depth Guard uses a median over a front-center ROI with a short temporal buffer and hysteresis to stabilize decisions.
  • On trip, the server issues an immediate stop and blocks forward commands; steering/backward remain available to recover.
  • Soft-ramp PWM and duty caps reduce mechanical shock and keep the platform stable.

Highlights

  • A compact, depth-only safety layer replaced a more complex plan and improved reliability.
  • Repeatable left-side bypass around a bottle line using capped probe and small corrective bias.
  • Clear code paths and real-time UI shortened the debug loop substantially.

Development notes

Scope and decisions

  • Initial goal: full navigation. Timeline made that unrealistic on the hardware available.
  • Change in scope: focused on a dependable depth safety layer and a deterministic bypass maneuver.
  • Signal stabilization: median ROI + short buffer + hysteresis outperformed raw minimum-distance methods.

Failure cases and fixes

  • Occasional slow-down without full stop → added a hard stop latch and blocked forward at the route.
  • Over-rotation on the first probe → capped the probe duration and added a minor right-bias after each forward pulse.
  • Server stalls under mixed loads → separated safety/mapping threads from Flask routes to avoid blocking.

Path to a stable demo

  • Bring up streams (depth, map) to validate sensing.
  • Implement guard; verify consistent stopping at a fixed distance.
  • Implement single-side (left) maneuver to reduce ambiguity and ease tuning.
  • Polish the UI to surface the relevant signals while driving.
